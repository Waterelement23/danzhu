# 地面弹珠 1V1 技术设计

日期：2026-09-07

状态：首版已实现，运行与验证方式见 [README](../../../README.md)。物理、规则和真实双客户端已有自动化验证，容量与实机性能尚未完成认证。

关联：[游戏设计文档](./2026-09-07-marble-duel-design.md)。游戏文档定义怎么玩、胜负和体验要求；本文定义用什么技术以及如何实现。玩法变更先更新游戏文档，再同步本文受影响的技术约束。本文不重复维护超时、缩圈和最大轮数等规则数值。

## 技术选型与理由

| 部分 | 首版采用 | 职责与选择理由 |
| --- | --- | --- |
| 开发语言 | TypeScript | 客户端、服务器与共享核心使用同一语言，共享协议与配置类型；运行时仍需校验网络输入 |
| 3D 画面 | Three.js | 绘制地形、玻璃球、石块、阴影及固定镜头；与独立物理核心组合，符合浏览器优先的范围 |
| 3D 物理 | Rapier 3D（JavaScript / WebAssembly） | 计算刚体、重力、碰撞、旋转和落地反弹；浏览器练习与服务器使用相同版本和物理配置 |
| 服务端运行时 | Node.js | 运行房间服务和无画面的权威物理世界，复用 TypeScript 核心 |
| 联网框架 | Colyseus | 房间生命周期、消息、状态同步和重连；游戏规则与物理仍由项目实现 |
| 前端构建 | Vite | 浏览器开发服务器、资源构建与打包 |

首版界面采用 HTML/CSS 与 TypeScript，暂不额外引入 React 等 UI 框架。Three.js 是渲染库，不负责房间或物理；Rapier 不负责绘制地形；Colyseus 不会自动实现游戏胜负规则。

当前是小场景、两颗球、浏览器分享试玩的目标，因此采用上述组合。Godot、Unity 等完整引擎保留为未来原生客户端路线的候选，不在首版引入。代价是本项目需要自行组织场景、输入、资源和物理之间的接口，不具备完整引擎开箱即用的编辑器工作流。

不在设计阶段杜撰最新版本号。实施初始化时核对各库官方安装说明与兼容性，选择受支持的稳定版本，记录 Node.js 版本并提交包管理锁文件；客户端、服务端与练习模式共用同一 Rapier 版本。版本号及安装命令归后续项目 README 和依赖文件维护。

## 运行架构

```text
浏览器 A / B
  输入与界面 → 发球/击球等指令
                     ↓
            Node.js + Colyseus 房间
              校验身份、阶段与参数
                     ↓
            共享规则核心 + Rapier
              物理推进与首次事件判定
                     ↓
          状态快照 / 带时间的结算事件
                     ↓
浏览器：姿态插值 → Three.js 画面与结算界面
```

联网局只有服务器能创建正式弹珠、施加击球冲量和锁定胜负。客户端可即时画瞄准预览，但不能上传球位置、释放高度或胜负结论。服务器物理世界不依赖 DOM、WebGL 或 Three.js。

本机练习使用本地适配器运行同一套规则与物理；联网使用远程适配器。切换适配器不改变核心玩法，界面明确标注当前模式。首版不做客户端物理预测与回滚，也不依赖不同设备的模拟逐位一致。

## 地形生成与渲染

地形以一份版本化地图定义为源：网格尺寸、顶点高度、三角形索引、材质区域、石块形状和变换、发球线及边界。坐标统一为 Y 向上，X-Z 为水平面，使用米、千克、秒。

1. 程序生成规则网格高度，构成缓坡、浅坑和土包。首版固定地图，不在每台设备上独立随机生成。
2. Three.js 从顶点与索引创建可见地面，计算法线并赋予土地主材质。
3. 首版优先用同一顶点与索引创建 Rapier 静态三角网格碰撞体，以明确保证两者三角形划分一致。Rapier 高度场是后续替换选项；采用时必须验证轴向、网格尺度和三角形划分与渲染一致。
4. 石块以共用几何定义生成显示模型与静态凸碰撞体；优先让轮廓一致，再增加不影响碰撞的小纹理细节。

网格密度依据球径及最小有意义的凸起尺寸确定，不能把视觉纹理上的每粒沙都变成碰撞三角形。法线贴图只改变光照，影响运动的凸起必须存在于真实碰撞几何。检查网格接缝和细长三角形引起的异常弹起，并验证所选版本的内部边缘修正配置。

玻璃球使用 Three.js 的 MeshPhysicalMaterial 表达透射、折射率和厚度，辅以内部彩色结构与环境光。阴影帮助识别球的离地高度。透明材质与阴影按设备画质降级，画质设置不能改变服务器物理结果。首版程序化场景不强制依赖 Blender；后续精细模型采用下面的 Blender MCP 工作流。

### Blender MCP 精细建模工作流

按用户约定，后续需要制作精细弹珠内部结构、石块或场景装饰时，优先全局安装并配置 Blender MCP，通过 MCP 操作 Blender 创建和迭代模型。全局指当前用户可跨项目复用的工具安装与 MCP 配置，不将其作为游戏运行时依赖，也不要求系统级管理员安装。本次仅记录方案，尚未执行安装。

启用时先检查已有 Blender 与 MCP 配置，存在可用连接则复用。需要安装时核对所选实现的维护状态、Blender 版本兼容性和当前客户端接入说明，同时安装/启用所需 Blender 插件并验证连接。可参考社区项目 [ahujasid/blender-mcp](https://github.com/ahujasid/blender-mcp)；它不是 Blender 官方实现，具体实现和版本在启用时确定，不混用不同实现的插件与服务端。

通过 MCP 完成建模、材质、预览和修改，保存可编辑的 `.blend` 源文件，并导出面向游戏的 glTF/GLB 资产交给 Three.js 加载。保留必要的生成脚本或操作记录，便于后续复现和调整。模型入库前检查单位、尺寸、原点、坐标转换、法线、材质表现、面数与贴图大小，并在实际游戏镜头下检查效果。

精细显示模型与物理碰撞仍分别管理：小装饰无需碰撞；会改变球轨迹的石块或地形必须有匹配的 Rapier 碰撞形状，不能直接将高面数美术模型无条件用于实时碰撞。Blender MCP 仅参与开发期资产生产，玩家浏览器和对战服务器无需安装 Blender 或连接 MCP。

## 出手、腾空和接触

弹珠使用动态球体刚体，保留三个平移自由度和旋转自由度，不锁定高度。半径、质量与转动惯量须相互一致，不能仅为画面把碰撞球和可见球设成明显不同的大小。

- 开局先手：球心水平投影在发球线上，服务器从固定释放高度创建球，施加向场内的水平冲量；重力产生下落，接触求解产生落地反弹。
- 后手入场：服务器在发球线地面支撑处创建贴地球，沿支撑面切向施加冲量。
- 后续击球：保留实际停留位置与姿态，只对已有球施加切向冲量，不重新生成或抬球。

贴地切向可通过将水平瞄准方向投影到支撑面的切平面后归一化得到；使用有效的地面接触法线，不把侧面石块碰撞法线直接当成地面。退化方向或缺少稳定支撑时拒绝出手并保持同步，避免无效数值进入物理世界。

腾空后由重力推进三维速度，不施加地面滚动阻力、不按地形高度贴地。是否越凸起腾空由速度和接触决定。落地采用恢复系数和接触摩擦，滚动阶段补充耗能模型；仅用全局阻尼不能表达地面材质差异。

材料参数按玻璃与地面/石块的接触组合校准，明确恢复系数与摩擦的组合规则。不能假定分别给两个物体赋值，就自动得到期望的材料对参数。沙地首版是耗能近似，不模拟颗粒或形变。稳定支撑、速度阈值及持续时间共同决定停稳，空中最高点不算停稳。

## 时间推进与胜负事件

物理采用固定步长，初始调试值为 1/120 秒；渲染使用浏览器帧循环。用累计时间推进固定步，不以浏览器帧率或不稳定定时器间隔直接作为物理步长。服务器过载时限制单次补算工作量并监测积压，不擅自加大物理步长；持续无法跟上时中止异常对局并给出原因。

为运动中的弹珠开启 CCD，限制最大冲量。CCD 用于降低高速漏碰撞风险，并不保证提供游戏需要的全部事件时间信息，也不能直接以事件回调顺序判胜负。

初版采用接近候选事件时细分微步、在微步内比较三维接触与水平越界时刻的方案，具体步长见末尾实现记录。碰撞后的速度会改变，因此不能将整个正常步的起终点连起来并假定中间一直匀速。世界快照恢复与重演是原设计的候选方案，当前实现不依赖它，也不假定引擎通知直接给出精确接触时刻。

将事件定位误差目标初设为不大于 0.1 毫秒；初版已通过同子步先命中/先出界及跨微步冲突窗口对照，但这不是对所有复杂地形轨迹的误差证明。精度内不可区分的事件按游戏设计的平局规则处理。结果一旦锁定，后续事件只能用于展示。三维球体真实接触才是命中，越界按球心 X-Z 投影计算。

## 房间同步与连接

输入消息包含动作编号、对局编号、回合序号，以及归一化的方向/力度；发球额外包含沿线位置参数。服务端检查会话、席位、阶段、数值有限性与范围，并拒绝重复或过期动作。具体时间限制遵循游戏设计。

同步状态至少包括地图/物理配置版本、对局与回合编号、阶段、当前玩家、是否已发球、球的三维位置及四元数、当前边界、服务器时间和结算原因。地图几何在入房时加载或校验，不随每帧快照重复传输。

初始尝试约 20 次/秒广播姿态状态，浏览器使用短缓冲进行插值，旋转用四元数插值。此频率和缓冲长度须通过弹跳与高速碰撞画面测试调整，尤其避免稀疏快照跨过落地点时穿地。可在碰撞/落地时补发关键姿态；不能用客户端任意贴地修正掩盖错误。

结算消息带物理事件时间，客户端在插值播放到该时刻时显示结果，避免画面尚未碰到就突然宣布获胜。收到结果后立即禁止新操作；不等待客户端动画结束才在服务器判胜。

使用 Colyseus 房间与重连生命周期，房间码是加入入口，不是身份凭据。保留席位时通过独立会话凭据恢复身份。断线、暂停输入计时、当前击球完成和超时判负按游戏设计实现；框架提供连接能力，不能替代这些规则。

## 部署与验收

开发时 Vite 提供页面，Node.js 运行独立房间服务。正式部署为静态前端加持续运行的 Node.js 服务，经 HTTPS/WSS 对外提供访问；需要支持 WebSocket 升级。首版房间存内存，单实例起步，不引入数据库或 Redis。服务重启会丢失对局，客户端必须显示连接中断/对局失效，不能声称支持跨重启恢复。

服务器容量通过并发房间压测确定，不能由“只有两颗球”推断可支持多少在线用户。记录物理步耗时、调度积压、快照带宽和内存；网页记录帧时间与资源大小。后续多实例要考虑房间路由和状态归属，首版不提前实现。

验证先后顺序：

1. 物理试验：高位落地反弹、贴地滑动到滚动、地面耗能、坡面离地与回落、几何接缝稳定性。
2. 判定试验：高速 CCD、同子步相反事件顺序、空中越顶与实际接触、停稳与睡眠。
3. 联网集成：两个独立客户端正常对战、非法输入、重复动作、重连、服务器断开和房间回收。
4. 浏览器体验：桌面/触屏发球、阴影与高度辨识、弹跳插值、结算时序及画质降级。

释放高度、摩擦/恢复系数、滚动阻力、网格密度、事件定位精度、同步频率与性能容量仍需上述试验给出结果。技术选型已经写定不代表这些指标已验证；若引擎无法满足核心判定，应先更新技术决策再进入完整游戏开发。

## 初版实际实现记录

- 运行时采用 Node.js 24；精确依赖见项目依赖文件，含 Three.js 0.185.1、Rapier 0.20.0、Colyseus core 0.18.11。
- 同一份 64 分段网格创建显示和碰撞地形，四块石头使用相同的细分二十面体顶点。当前场地半边长 1.5 米、球半径 0.062 米、释放高度 0.8 米，属于原型调参值。
- 正常物理步长为 1/120 秒；接近球体或边界时使用 1/15360 秒微步并在微步内估计扫掠事件时间。首次事件后的 0.1 毫秒比较窗口跨微步处理冲突。非线性运动仍是数值近似，不承诺无限精度。
- 引擎预测接触通知不直接判命中，还需实际接触距离或三维扫掠证据。初版采用微步方案，未采用世界快照回放；已验证相反事件顺序与高速碰撞。
- 网络每 50 毫秒发送快照，客户端缓冲并延迟 100 毫秒播放；结算展示等待显示时间到达事件时间。未实现复杂客户端预测。
- 接地阻力只在支撑接触时生效，普通击球使用实际支撑接触法线。高位释放和贴地入场由服务器根据阶段决定。
- 物理 WASM 按需加载；当前兼容包物理块约 2.86 MB，gzip 约 1.10 MB。首版保留此构建体积提示，后续可改用独立 WASM 资源进一步优化。
- 程序化美术、鼠标及触屏指针输入已接入；精细瞄准提供滑条操作。手机布局已检查，真实设备性能仍需试玩；本版未使用 Blender。
