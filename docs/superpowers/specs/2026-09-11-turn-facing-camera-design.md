# 双人对战的出手朝向镜头方案

状态：用户已批准，已完成实现、本地及公网验证并部署；部署记录见实施计划。

## 评估与推荐

值得优化。以自己弹珠到对手弹珠的方向组织瞄准视野，能让玩家更直接判断偏左、偏右以及沿途障碍，尤其有利于手机操作。这属于镜头与操作体验优化，不改变命中精度、物理轨迹或竞技规则。

推荐只调整当前操作者的本地镜头。让双方同时旋转会打断观战者对场地的观察；让镜头随拖动方向持续旋转会造成目标漂移、增加眩晕与误操作，因此不采用这两种方案。

保持现有透视相机与 58° 俯角，改变水平朝向及必要的取景位置。出手视角中自己弹珠位于下方，对手弹珠位于上方；不切换为贴地第一人称。任意方向的两球连线与矩形边界无法同时保持正向，出手视角允许矩形边斜向显示；固定全景保持原有棋盘朝向。

## 状态与切换规则

| 游戏状态 | 操作者看到的镜头 | 另一方看到的镜头 |
| --- | --- | --- |
| 等待开局 | 固定全景 | 固定全景 |
| 任意玩家首次入场发球，包括后手贴地发球 | 固定朝向的发球视角 | 相同固定朝向的发球视角 |
| 两球已经入场，轮到自己出手 | 从自己弹珠后方朝向对手 | 固定全景 |
| 按住瞄准、蓄力 | 锁定当前镜头 | 固定全景 |
| 松手后弹跳、滚动、碰撞或出界 | 保持本次出手朝向，必要时只平滑拉远 | 固定全景 |
| 无胜负，弹珠停稳并交接回合 | 原操作者回到全景；新操作者进入自己的出手视角 | 各端独立过渡 |
| 已判胜负、等待 1.8 秒结算 | 保持这一击的视角，让玩家看清结果 | 固定全景 |
| 再战或返回大厅 | 恢复固定朝向 | 恢复固定朝向 |

“相同发球视角”指同一世界朝向和发球区域构图规则。屏幕宽高比不同不强求逐像素相同。发球阶段不沿用单方面自动放大偏移，以免双方观察朝向和发球上下文不同。

## 取景与操作

- 以已停稳的权威弹珠位置计算从自己到对手的地面方向，相机位于这个方向的反侧；保持世界竖直方向，不歪斜画面。
- 两颗球及其间障碍必须同时进入安全视口。构图稍偏向对手，给自己的球下方留出拖动空间，避开手机底部操作区和顶部状态栏。
- 根据两球距离和屏幕尺寸计算相机距离，不能照搬当前固定 1.5 倍放大。近距离限制最大放大，远距离优先同时容纳两球；可见边界参与安全边距计算。
- 回合切换采用约 0.4–0.6 秒平滑过渡，水平旋转走最短角度；若正好相差 180°，固定选择同一旋转方向，避免反复跳变。
- 不围绕正在移动的对手不断重新取向，也不在出手瞬间旋转回全景。运动需要更多空间时，只沿当前朝向拉远，不追着球转圈。
- 用户在过渡途中开始瞄准时，立即冻结当前实际相机姿态，并按该姿态解释整次手势。取消瞄准后才恢复目标镜头，不额外延长服务器回合计时。
- 桌面与手机均提供“全景 / 出手视角”切换入口。手动选择在本回合保持，新的可出手回合再默认切入出手视角；蓄力期间禁用切换。发球阶段不出现无效的出手视角入口。
- 对手位置缺失或两球水平距离过小时保持稳定全景；断线失去操作权时清除蓄力并平滑回全景。窗口变化保留合法朝向，手势期间发生横竖屏切换则取消手势，避免误发射。
- 尊重减少动态效果偏好，使用即时切换。回合身份与发球提示继续保留，不能仅靠镜头表达轮到谁。

## 技术落点

1. 新建 `src/client/turn-camera.ts`：管理固定全景、发球、出手、运动观察的状态，计算目标朝向、焦点、距离和插值；纯计算与 Three.js 场景渲染分开，便于测试。
2. 修改 `src/client/scene.ts`：当前 `updateCamera` 只有固定方位，`resize` 也按固定方位拟合棋盘。改为按相机局部坐标检查两球、边界和安全视口，并将新相机过渡加入 `renderActive`，避免静止帧率拖慢旋转。
3. 修改 `src/client/main.ts`：显式传入本地玩家身份、操作权、双方入场状态及阶段；镜头变化以回合事件触发，不随每个网络快照反复触发。本机练习可复用当前操作者身份以方便测试，首版验收以联网模式为主。
4. 修改 `src/client/match-ui.ts` 与 `scene.ts` 的触控输入：现有 `touchAim` 默认屏幕方向就是固定世界 X/Z。改为将屏幕向量按冻结的相机地面前向和右向转换为世界方向，保留按屏幕拖动距离计算力度的方式。桌面射线投影也按当前相机验证，不另做世界轴旋转。
5. 复核瞄准线、发球落点、玩家标签和空间音效：都以同一实际相机为准。焦散太阳方向始终固定在世界中，相机旋转不能让太阳或场地跟着旋转。
6. 复用现有反射与遮挡机制。旋转期间允许更新镜面，停稳后重新缓存；静态阴影不因相机旋转重算。不增加相机渲染通道，保留手机活动 30 fps、静止 15 fps 及现有像素预算。

## 院落遮挡与模型完整性

当前房屋按固定视角补齐可见区域。新镜头可能看到原先不可见的背面、屋檐底面，也可能被房屋或树冠挡住两颗弹珠，必须在实施时检查，不能仅提交相机数学修改。

首选沿目标朝向调整取景距离与焦点，保持 58° 俯角，寻找同时可见的构图。若仍被高大建筑或树冠遮挡，第一版回退到固定全景，并保留清晰的状态提示；不自动隐藏承载弹珠或影响碰撞的实体。针对常见方向补齐必要可见面后，再扩大出手视角可用范围。

预览检查覆盖 8 个水平朝向，包含四角、两球贴边、最大/最小球距、手机横竖屏。若常用球位频繁回退全景，则不能视作完成，需要先解决院落遮挡再发布。验收时保留可量化的回退案例列表。

## 实施顺序与验收

1. 先实现并测试纯镜头计算与回合状态，再接入桌面预览；固定物理世界、网络消息与胜负规则。
2. 同步接入手机拖动方向变换、手势锁定、两球自动取景及手动全景入口。
3. 检查全部方位的模型遮挡、可见面、反射、音效左右定位，补齐与该功能直接相关的问题。
4. 两个独立客户端验证：同一时刻操作者进入出手视角，观战者保持全景；双方发球均使用固定朝向；击球后不突然转向，碰撞和出界直到结算均清楚可见。

自动化覆盖方位 0/90/180/270° 和 ±180° 插值边界、两球贴边与近距离退化、两次发球例外、切换操作权、拖动锁定和不同朝向下同样手势的世界方向。原有联网、判胜、出界延续运动、发球预览和渲染预算测试必须继续通过。

最后在 iPhone 16 Pro 的 Safari 与微信中验证：向后拉始终按屏幕预期方向发射，两球及瞄准线清楚可见，转场无闪烁或过度旋转，长时间使用未明显增加发热。桌面模拟结果不替代真机结论。
